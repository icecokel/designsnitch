# designsnitch

AI가 만든 UI 코드에서 디자인이 틀린 곳을 찾아내는 라이브러리입니다. 기준은 프로젝트의 디자인 시스템입니다. 토큰과 컴포넌트 규칙을 벗어난 곳을 찾고, 무엇으로 고치면 되는지 알려줍니다.

> **상태:** 아이디어 단계. 아직 구현된 코드가 없습니다. 아래 내용은 목표 설계이며, 정해지지 않은 부분은 [미정 사항](#미정-사항)에 모아 두었습니다.

## 왜 필요한가

AI 에이전트가 만든 UI는 얼핏 보면 그럴듯하지만, 자세히 보면 조금씩 틀려 있는 경우가 많습니다.

- primary 색을 토큰 대신 hex로 박아 둬서, 다크 모드로 바꾸면 그 부분만 색이 그대로 남습니다.
- 버튼 색이 primary와 거의 같지만 미묘하게 다릅니다.
- 간격이 16이어야 할 곳에 15나 18이 들어가 있습니다.
- 디자인 시스템에 Button이 있는데 버튼을 새로 만들어서, 높이가 조금 낮거나 focus 스타일이 없습니다.

이런 차이는 리뷰에서 눈으로 잡기 어렵습니다. designsnitch는 코드를 분석해서 이런 곳을 찾아냅니다.

## 판단 기준

| 등급 | 의미 |
| --- | --- |
| **오류** | 디자인 시스템에 쓸 토큰이나 컴포넌트가 있는데 쓰지 않았습니다. 지금 화면이 같아 보여도, 디자인 시스템이 바뀌면 이 코드만 따라가지 않습니다. |
| **경고** | 디자인 시스템에 맞는 토큰이 없습니다. 새 값이 정말 필요한 건지 실수인지 사람이 판단해야 합니다. |

## 감지 대상 한눈에 보기

| 대상 | 오류 | 경고 |
| --- | --- | --- |
| 색 | 토큰이 있는 색을 hex로 씀 | 토큰이 없는 hex |
| 간격, 폰트 크기, radius | 토큰 값과 같은 숫자를 직접 씀 | 스케일에 없는 값 |
| 컴포넌트 | 디자인 시스템 컴포넌트가 있는데 raw 태그나 직접 만든 컴포넌트를 씀 | 없음 |

## 감지 대상

### 1. 색

#### 토큰이 있는 색을 hex로 씀 (오류)

hex 값이 토큰 값과 같으면, 그 토큰을 쓰라고 알려줍니다.

```
src/features/checkout/PayButton.tsx:12:18  오류
  #3B82F6 은 토큰 --color-primary-500 의 값입니다.
  → var(--color-primary-500) 를 사용하세요.
```

토큰이 테마마다 다른 값을 가지면, 어느 테마의 값과 같든 같은 방식으로 잡습니다.

```
src/features/checkout/Card.tsx:8:14  오류
  #FFFFFF 는 라이트 테마의 --color-surface 값입니다.
  다크 테마에서는 --color-surface 가 #111827 이므로 이 부분만 흰색으로 남습니다.
  → var(--color-surface) 를 사용하세요.
```

#### 토큰이 없는 hex (경고)

팔레트에 없는 색입니다. 팔레트 색과 아주 가까우면 근사값이나 오타일 가능성이 크므로, 가장 가까운 토큰을 함께 제시합니다.

```
src/features/checkout/PayButton.tsx:20:18  경고
  #3B82F5 는 팔레트에 없는 색입니다.
  가장 가까운 토큰: --color-primary-500 (#3B82F6)
```

### 2. 간격, 폰트 크기, radius

#### 토큰 값과 같은 숫자를 직접 씀 (오류)

```
src/features/checkout/Summary.tsx:30:5  오류
  padding 16px 는 토큰 --space-4 의 값입니다.
  → var(--space-4) 를 사용하세요.
```

#### 스케일에 없는 값 (경고)

```
src/features/checkout/Summary.tsx:42:5  경고
  padding 15px 는 간격 스케일에 없습니다.
  가장 가까운 토큰: --space-4 (16px)
```

### 3. 컴포넌트

#### 디자인 시스템 컴포넌트를 쓰지 않음 (오류)

디자인 시스템 경로 밖에서 다음을 찾습니다.

- 디자인 시스템 컴포넌트가 대체하는 raw 태그(`button`, `input`, `select`, `dialog` 등)
- 기존 디자인 시스템 컴포넌트와 역할이 같은, 직접 만든 컴포넌트

직접 만든 컴포넌트는 디자인 시스템 컴포넌트와 스타일을 비교해서, 다른 점이 있으면 함께 보여줍니다. 바꿨을 때 화면이 어떻게 달라지는지 미리 알 수 있습니다.

- 크기, padding, radius, 색이 다른지
- hover, focus, disabled 같은 상태 스타일이 빠졌는지

```
src/features/checkout/ConfirmModal.tsx:5:10  오류
  raw <dialog> 를 디자인 시스템 밖에서 사용했습니다.
  → @/components/ui/Dialog 를 사용하세요.
```

```
src/features/checkout/ConfirmButton.tsx:4:10  오류
  디자인 시스템 Button 과 역할이 같은 컴포넌트입니다.
  - height 36px (Button: 40px)
  - :focus-visible 스타일 없음
  → @/components/ui/Button 을 사용하세요.
```

> 위 출력들은 동작을 설명하기 위한 예시이며, 실제 출력 형식은 아직 정해지지 않았습니다.

## 동작 방식

1. **디자인 시스템 읽기:** 토큰 소스에서 색, 간격, 폰트, radius 토큰과 테마별 값을 읽고, 컴포넌트 목록에서 각 컴포넌트의 스타일을 읽습니다.
2. **코드 분석:** 검사할 코드를 AST로 파싱합니다. 문자열 검색이 아니라 구문 구조를 보기 때문에 주석이나 무관한 문자열은 잡지 않습니다.
3. **비교:** 코드에 나온 색과 수치를 토큰 값과 비교하고, raw 태그와 직접 만든 컴포넌트를 디자인 시스템 컴포넌트와 비교합니다.
4. **보고:** 위반 위치(파일, 줄, 열), 등급, 고칠 방법(대신 쓸 토큰이나 컴포넌트)을 알려줍니다.

## 다른 프로젝트에서 쓰기

designsnitch는 특정 디자인 시스템에 묶이지 않습니다. 프로젝트마다 다음 두 가지를 설정하면 됩니다.

| 설정 | 설명 |
| --- | --- |
| 토큰 소스 | 색, 간격, 폰트, radius 변수가 정의된 CSS 파일 (테마별 값 포함) |
| 컴포넌트 목록 | 디자인 시스템 컴포넌트가 있는 경로와, 각 컴포넌트가 대체하는 raw 태그 |

설정 파일 형식과 API는 구현을 시작할 때 정합니다.

## 범위 밖

- **화면별 시안과의 비교:** Figma 같은 시안 파일을 읽어서 "이 화면이 시안대로인가"를 보는 일은 하지 않습니다. 기준은 디자인 시스템 하나입니다.

## 미정 사항

| 항목 | 선택지 |
| --- | --- |
| 결과를 쓰는 쪽 | 사람(CI, PR 코멘트) / AI 에이전트(생성 후 스스로 수정) / 둘 다 |
| 지원 스택 | 프레임워크(React 등), 스타일 방식(CSS, CSS-in-JS, Tailwind 등)의 지원 범위 |
| 근사값 판정 | 토큰이 없는 색이나 값을 볼 때, 얼마나 가까워야 가장 가까운 토큰을 제시할지 |
| 역할 판정 | 직접 만든 컴포넌트가 어떤 디자인 시스템 컴포넌트와 역할이 같은지 판단하는 방법 |
